📖 The Story — 3 Acts, 23 Chapters

Every chapter of the story is one design pattern, and every chapter exists as a runnable program in both cpp/ and python/. The three acts are exactly the three GoF categories — that mapping alone is worth memorizing:

  • Act 1 — Opening Day = Creational: how things get created.
  • Act 2 — The Expansion = Structural: how things get wired together.
  • Act 3 — The Daily Grind = Behavioral: how everyone talks to each other.

Act 1 — Opening Day (Creational, 5 patterns)

Chapter 1 · Singleton — The One Cash Register

You buy exactly ONE cash register. Every barista shares it; a second one would ruin the day's totals.

Remember: one till, shared by all → one instance, global access
C++ · Python

Chapter 2 · Factory Method — Hiring Baristas

Every barista follows the same serving routine, but each specialist decides WHICH drink they craft.

Remember: same routine, subclass picks the product
C++ · Python

Chapter 3 · Abstract Factory — The Franchise Kits

The Italian kit ships a lever machine WITH porcelain cups; the Japanese kit a siphon WITH ceramic cups. Families never mix.

Remember: a whole kit of matching products → family of objects
C++ · Python

Chapter 4 · Builder — "Can I Get That With Oat Milk?"

Large, two shots, oat milk, extra hot... drinks are assembled step by step; the menu board keeps the famous recipes.

Remember: complex order built step by step → fluent builder + director
C++ · Python

Chapter 5 · Prototype — The Drink of the Day

Don't invent from scratch: CLONE yesterday's bestseller card and tweak one thing. The original stays in the box.

Remember: clone the recipe card → copy an existing object
C++ · Python

Act 2 — The Expansion (Structural, 7 patterns)

Chapter 6 · Adapter — Grandpa's Grinder

The kitchen expects grind(); the heirloom only knows turnCrank(). You build a fitting, not a new grinder.

Remember: old crank in a new kitchen → translate one interface to another
C++ · Python

Chapter 7 · Bridge — Any Drink, Any Machine

Without care you'd need HomeLatte, IndustrialLatte, HomeCappuccino... instead, every drink HOLDS a machine.

Remember: drinks × machines stay independent → split the two hierarchies
C++ · Python

Chapter 8 · Composite — The Menu Grows

Sections inside sections inside the menu. You ask a croissant or a whole combo the same question: "what does this cost?"

Remember: item and section answer the same question → tree, uniform interface
C++ · Python

Chapter 9 · Decorator — Toppings, Toppings, Toppings

Milk wraps espresso, sugar wraps milk, whipped cream wraps sugar. Every topping adds its price and description.

Remember: toppings wrap the drink → add behavior by wrapping
C++ · Python

Chapter 10 · Facade — One Counter to Rule Them All

Inventory, brewing, payment, loyalty — the customer sees none of it. They say "one latte please" and the counter orchestrates.

Remember: "one latte please" → one simple call hides the subsystem
C++ · Python

Chapter 11 · Flyweight — A Thousand Tickets, Three Drinks

Thousands of tickets, a handful of drink types. Each ticket carries only its number — the recipe is shared.

Remember: tickets share the drink definition → share intrinsic state
C++ · Python

Chapter 12 · Proxy — The Secret Recipe Book

The stand-in looks exactly like the recipe book, but only walks to the safe the FIRST time someone asks.

Remember: stand-in for the book in the safe → placeholder controls access
C++ · Python

Act 3 — The Daily Grind (Behavioral, 11 patterns)

Chapter 13 · Chain of Responsibility — "I'd Like a Refund"

Barista refunds $5, shift manager $50, owner $500. The complaint climbs until someone can handle it.

Remember: the complaint escalates → request travels a chain of handlers
C++ · Python

Chapter 14 · Command — Tickets on the Rail

Orders become ticket OBJECTS clipped to the rail. Customer changed their mind? Pull the last ticket off (undo).

Remember: order = ticket object → request as object, queue + undo
C++ · Python

Chapter 15 · Interpreter — The Regulars' Shorthand

"espresso + milk − coupon" — the till evaluates the regulars' tiny order language, one class per grammar rule.

Remember: the till speaks shorthand → class per grammar rule, interpret()
C++ · Python

Chapter 16 · Iterator — The Vinyl Crate

Flip through the playlist song by song — but nobody touches the crate or knows how the records are stored.

Remember: flip through, never touch the crate → traverse without exposing internals
C++ · Python

Chapter 17 · Mediator — The Counter Intercom

The shop was a shouting match. Now staff speak into the intercom and it relays — nobody needs to know who's on shift.

Remember: intercom instead of shouting → central hub replaces many-to-many
C++ · Python

Chapter 18 · Memento — The Chalkboard Specials

Photograph the board before each risky idea. Durian latte flops? Restore from the last photo. The drawer never reads the photos.

Remember: photo of the chalkboard → snapshot & restore without exposing state
C++ · Python

Chapter 19 · Observer — "Order 42 Is Ready!"

When the barista finishes, the pickup screen flashes AND the phone buzzes — the barista doesn't know who's listening.

Remember: screen + phone both react → one subject notifies many observers
C++ · Python

Chapter 20 · State — The Moody Espresso Machine

Idle accepts an order; loaded beeps at a second one but brews on demand. Each mood is its own class — no giant if/else.

Remember: the machine's moods → behavior delegated to swappable state objects
C++ · Python

Chapter 21 · Strategy — Happy Hour

Same latte, different price rule: regular, happy hour, member. Swap the rule when the clock strikes five.

Remember: swap the pricing rule → interchangeable algorithms
C++ · Python

Chapter 22 · Template Method — The House Ritual

Boil, brew, pour, finish — always in that order. Only HOW you brew and the finishing touch differ per drink.

Remember: the ritual never changes, the steps do → fixed skeleton, overridable steps
C++ · Python

Chapter 23 · Visitor — The Inspectors

The nutritionist counts calories, the accountant prints tags. Menu items just ACCEPT them — new inspectors need no menu changes.

Remember: inspectors visit the menu → new operations without touching the classes
C++ · Python

🎓 Mastery Questions

Work through the levels in order. Click each question to reveal the answer — but only after committing to your own.

Level 1 — Story recall (can you name the pattern?)

1. A complaint travels barista → shift manager → owner until someone can refund it. Which pattern, and what's the defining property?
Chain of Responsibility. The sender knows only the FIRST handler; each handler either handles the request or forwards it. Sender and final handler are decoupled.
2. Every franchise kit ships a machine and cups that always match. Which pattern, and what guarantees the "matching"?
Abstract Factory. One concrete factory (ItalianKit) creates ALL products of one family, so clients can't accidentally mix a siphon with porcelain — they only ever hold one factory.
3. The pickup screen AND the customer's phone both react when order 42 is done. Pattern? Who knows about whom?
Observer. The subject (pickup counter) holds a list of observers and notifies them; it doesn't know their concrete types. Observers know the subject only to subscribe.
4. You photograph the chalkboard before writing "durian latte". Pattern, and name the three roles.
Memento. Originator = chalkboard (creates/restores snapshots), Memento = photo (opaque state), Caretaker = drawer (stores photos but never reads them).
5. Milk wraps espresso, whipped cream wraps milk. Pattern, and why isn't this just subclassing?
Decorator. Subclassing would need a class per combination (MilkSugarWhipEspresso…); wrapping composes any combination at RUN TIME, and each wrapper shares the Coffee interface.
6. The till charges half price after 5pm because you swapped the pricing rule. Pattern, and what stays unchanged when rules change?
Strategy. The context (the till) stays unchanged — it programs against the PricingStrategy interface; only the plugged-in algorithm object changes.
7. "Boil, brew, pour, finish" — the order never changes but tea steeps while coffee drips. Pattern, and where does the fixed order live?
Template Method. The fixed order lives in the BASE class's non-overridable template method (prepare()); subclasses override individual steps (brew, the addCondiments hook).
8. One stand-in object delays the trip to the safe until the first recipe lookup. Pattern + which variant?
Proxy — specifically a virtual proxy (lazy initialization). Other variants: protection, remote, caching/logging proxy.

Level 2 — The classic confusions (pattern vs pattern)

9. Strategy vs State — both swap an object behind an interface. What's the real difference? Use the café.
WHO drives the change. Strategy: the client/context picks the algorithm from outside (YOU flip the till to happy hour). State: the object transitions ITSELF as events occur (the espresso machine moves idle→loaded→idle on its own). Also: strategies are usually independent of each other; states know about their sibling states to transition.
10. Adapter vs Bridge vs Facade — all "structural glue". One sentence each, café edition.
Adapter: makes an EXISTING incompatible thing fit (grandpa's crank → grind()). Bridge: designed UP FRONT so two dimensions (drinks × machines) evolve independently. Facade: doesn't translate anything — it SIMPLIFIES a whole subsystem behind one call ("one latte please").
11. Decorator vs Proxy — both wrap one object and share its interface. Difference in intent?
Decorator ADDS behavior the client asked for (toppings change description and price), usually stacked freely by the client. Proxy CONTROLS ACCESS (laziness, permissions, caching) and the client typically doesn't know or care whether it has the real object — it's about plumbing, not features.
12. Composite vs Decorator — both are recursive wrappers. Structural difference?
Composite nodes hold MANY children and aggregate over them (a menu section sums all its items). Decorator wraps exactly ONE inner object and enriches it. Composite is about part–whole trees; decorator about layered behavior.
13. Factory Method vs Abstract Factory — both create things. Distinguish them with baristas and kits.
Factory Method: ONE creation point, deferred to subclasses — each barista subclass decides its single signature drink. Abstract Factory: an OBJECT with several factory methods producing a consistent FAMILY — the kit creates machine AND cups that must match. (An abstract factory is often implemented as a set of factory methods.)
14. Mediator vs Observer — both decouple communicators. When would you pick each in the café?
Mediator for PEER coordination with routing logic: staff talk through the intercom, which decides who hears what (many-to-many → hub). Observer for one-way BROADCAST: the counter announces, every subscriber reacts; the subject has no routing logic and doesn't expect replies.
15. Command vs Strategy — both wrap "something callable" in an object. Difference?
Command binds a receiver + action + arguments into a self-contained REQUEST ("make an oat latte at the kitchen") that can be queued, logged, undone. Strategy is a way of PARAMETERIZING an algorithm choice ("how to compute price") — no receiver, no undo, no history semantics.
16. Memento vs Prototype — both copy state. Difference in purpose and exposure?
Prototype clones a FULL working object to create a new independent one (today's special card). Memento exports a snapshot of INTERNAL state for the original object itself to restore later — and it stays opaque to everyone but the originator.

Level 3 — Scenario design (pick the pattern, defend it)

17. The POS must support "cancel last action" across sales, refunds and discounts, and replay the day's actions for auditing.
Command. Each action becomes an object with execute()/undo(); a history list gives undo, and replaying the list gives the audit log. Memento alone snapshots state but doesn't model the individual actions you must replay.
18. You're adding a loyalty mobile app, a kitchen display and a dashboard — all must react instantly when an order's status changes. More gadgets are coming.
Observer. Order status = subject; each gadget subscribes. New gadgets attach without touching the order code — the open/closed payoff is exactly why you avoid hard-coded notification calls.
19. A drink can be iced/hot/blended and brewed for dine-in, takeaway, or delivery packaging. You dread creating 9 classes (and 12 next month).
Bridge. Two independent dimensions (preparation style × serving mode): make one the abstraction and the other the implementation it holds. 3 + 3 classes instead of 3 × 3.
20. Your new supplier's API exposes fetchStockJSON() but your whole codebase calls getInventory() everywhere.
Adapter. Write one class implementing your getInventory() interface that delegates to fetchStockJSON() and converts the data. Don't touch the call sites, don't fork the supplier SDK.
21. Receipts need totals computed over arbitrary nesting: single items, combos, combos containing combos.
Composite. Item = leaf, combo = composite holding components; both implement priceCents(). The receipt code calls one method and recursion does the rest.
22. Baristas, ovens and the cashier currently hold references to each other; adding a delivery-rider role means touching 6 classes.
Mediator. Introduce a coordination hub (the intercom/dispatcher); every role talks only to it. Adding the rider means registering one more colleague, not editing six.
23. The order parser must evaluate gift-card rules like "(latte + muffin) - coupon20 if member". Marketing invents new rule words monthly.
Interpreter (for this small grammar): each rule word becomes an expression class; new words = new classes, no parser rewrite. If the language keeps growing in complexity, graduate to a real parsing library.
24. App startup creates 50,000 menu-tile objects and memory explodes; tiles differ only in position and badge text.
Flyweight. Move the heavy shared data (icon, styling, drink definition) into cached shared objects; keep position/badge as extrinsic state passed in. 50,000 contexts, a handful of flyweights.

Level 4 — Capstone coding challenges (no peeking — there's no answer to reveal)

  1. The Seasonal Special pipeline: combine Builder + Decorator + Strategy — build a base drink, wrap it with two toppings, price it under happy hour. One main(), three patterns cooperating.
  2. The Franchise simulator: Abstract Factory + Facade — a FranchiseOpener facade that takes any kit and runs the full opening-day sequence.
  3. Undo everything: Command + Memento — commands carry mementos so "undo" restores exact prior register state, not just the inverse action.
  4. The smart machine: State + Observer — the espresso machine publishes its state transitions; a maintenance dashboard observes and warns after N brews.
  5. Menu analytics: Composite + Visitor + Iterator — walk the whole menu tree with an iterator and let a visitor compute revenue per section.
