📖 The Story — 3 Acts, 23 Chapters

Every chapter of the story is one design pattern, and every chapter exists as a runnable program in cpp/ and python/ (English) and cpp-zh/ and python-zh/ (Chinese). The three acts are exactly the three GoF categories — that mapping alone is worth memorizing:

  • Act 1 — The Workshop = Creational: how robots get created.
  • Act 2 — The Assembly Line = Structural: how robots get wired together.
  • Act 3 — The Factory Floor = Behavioral: how everyone talks to each other.

🎓 Mastery Questions

Work through the levels in order. Click each question to reveal the answer — but only after committing to your own.

Level 1 — Story recall (can you name the pattern?)

1. A fault report travels technician → floor engineer → chief engineer until someone can authorize the repair. Which pattern, and what's the defining property?
Chain of Responsibility. The sender knows only the FIRST handler; each handler either handles the request or forwards it. Sender and final handler are decoupled.
2. Every product series ships a chassis and arms that always match. Which pattern, and what guarantees the "matching"?
Abstract Factory. One concrete factory (IndustrialSeries) creates ALL products of one family, so clients can't accidentally bolt a soft-grip arm onto a heavy chassis — they only ever hold one factory.
3. The dashboard AND the engineer's pager both react when unit 42 rolls off. Pattern? Who knows about whom?
Observer. The subject (assembly line) holds a list of observers and notifies them; it doesn't know their concrete types. Observers know the subject only to subscribe.
4. You snapshot the firmware before installing the "experimental laser module". Pattern, and name the three roles.
Memento. Originator = firmware config (creates/restores snapshots), Memento = snapshot (opaque state), Caretaker = backup vault (stores snapshots but never reads them).
5. Armor wraps the bot, solar charger wraps the armor. Pattern, and why isn't this just subclassing?
Decorator. Subclassing would need a class per combination (ArmoredSolarTalkingBot…); wrapping composes any combination at RUN TIME, and each wrapper shares the Robot interface.
6. The robot draws half power after you flip it to eco mode. Pattern, and what stays unchanged when rules change?
Strategy. The context (the robot) stays unchanged — it programs against the PowerStrategy interface; only the plugged-in algorithm object changes.
7. "Power on, self-test, load drivers, announce" — the order never changes but drones spin rotors while welders calibrate lasers. Pattern, and where does the fixed order live?
Template Method. The fixed order lives in the BASE class's non-overridable template method (boot()); subclasses override individual steps (selfTest, the announceReady hook).
8. One stand-in object delays booting the diagnostics suite until the first scan. Pattern + which variant?
Proxy — specifically a virtual proxy (lazy initialization). Other variants: protection, remote, caching/logging proxy.

Level 2 — The classic confusions (pattern vs pattern)

9. Strategy vs State — both swap an object behind an interface. What's the real difference? Use the factory.
WHO drives the change. Strategy: the client/context picks the algorithm from outside (YOU flip the robot to eco mode). State: the object transitions ITSELF as events occur (the robot moves idle→busy→idle on its own). Also: strategies are usually independent of each other; states know about their sibling states to transition.
10. Adapter vs Bridge vs Facade — all "structural glue". One sentence each, factory edition.
Adapter: makes an EXISTING incompatible thing fit (legacy crank → actuate()). Bridge: designed UP FRONT so two dimensions (robots × controllers) evolve independently. Facade: doesn't translate anything — it SIMPLIFIES a whole subsystem behind one call (the big green button).
11. Decorator vs Proxy — both wrap one object and share its interface. Difference in intent?
Decorator ADDS behavior the client asked for (upgrades change specs and price), usually stacked freely by the client. Proxy CONTROLS ACCESS (laziness, permissions, caching) and the client typically doesn't know or care whether it has the real object — it's about plumbing, not features.
12. Composite vs Decorator — both are recursive wrappers. Structural difference?
Composite nodes hold MANY children and aggregate over them (an assembly sums all its parts). Decorator wraps exactly ONE inner object and enriches it. Composite is about part–whole trees; decorator about layered behavior.
13. Factory Method vs Abstract Factory — both create things. Distinguish them with lines and series.
Factory Method: ONE creation point, deferred to subclasses — each assembly line subclass decides its single robot model. Abstract Factory: an OBJECT with several factory methods producing a consistent FAMILY — the series creates chassis AND arms that must match. (An abstract factory is often implemented as a set of factory methods.)
14. Mediator vs Observer — both decouple communicators. When would you pick each in the factory?
Mediator for PEER coordination with routing logic: robots talk through the tower, which decides who hears what (many-to-many → hub). Observer for one-way BROADCAST: the line announces, every subscriber reacts; the subject has no routing logic and doesn't expect replies.
15. Command vs Strategy — both wrap "something callable" in an object. Difference?
Command binds a receiver + action + arguments into a self-contained REQUEST ("weld seam #7 on the floor") that can be queued, logged, undone. Strategy is a way of PARAMETERIZING an algorithm choice ("how much power to draw") — no receiver, no undo, no history semantics.
16. Memento vs Prototype — both copy state. Difference in purpose and exposure?
Prototype clones a FULL working object to create a new independent one (the blueprint copy). Memento exports a snapshot of INTERNAL state for the original object itself to restore later — and it stays opaque to everyone but the originator.

Level 3 — Scenario design (pick the pattern, defend it)

17. The control panel must support "cancel last action" across welding, painting and transport jobs, and replay the day's actions for auditing.
Command. Each action becomes an object with execute()/undo(); a history list gives undo, and replaying the list gives the audit log. Memento alone snapshots state but doesn't model the individual actions you must replay.
18. You're adding a mobile app, a wall display and an alarm system — all must react instantly when a robot's status changes. More gadgets are coming.
Observer. Robot status = subject; each gadget subscribes. New gadgets attach without touching the robot code — the open/closed payoff is exactly why you avoid hard-coded notification calls.
19. A robot can be wheeled/tracked/hexapod and controlled by remote/AI/voice. You dread creating 9 classes (and 12 next month).
Bridge. Two independent dimensions (locomotion × control): make one the abstraction and the other the implementation it holds. 3 + 3 classes instead of 3 × 3.
20. Your new supplier's SDK exposes fetchPartsXML() but your whole codebase calls getInventory() everywhere.
Adapter. Write one class implementing your getInventory() interface that delegates to fetchPartsXML() and converts the data. Don't touch the call sites, don't fork the supplier SDK.
21. Cost reports need totals computed over arbitrary nesting: single parts, assemblies, assemblies containing assemblies.
Composite. Part = leaf, assembly = composite holding components; both implement costCents(). The report code calls one method and recursion does the rest.
22. Robots, cranes and conveyor controllers currently hold references to each other; adding a forklift role means touching 6 classes.
Mediator. Introduce a coordination hub (the dispatch tower); every machine talks only to it. Adding the forklift means registering one more colleague, not editing six.
23. The shift scheduler must evaluate rules like "(weld + paint) - powersave if night". Engineers invent new rule words monthly.
Interpreter (for this small grammar): each rule word becomes an expression class; new words = new classes, no parser rewrite. If the language keeps growing in complexity, graduate to a real parsing library.
24. Startup creates 50,000 drone objects and memory explodes; drones differ only in serial number and docking bay.
Flyweight. Move the heavy shared data (model name, blueprint, mesh) into cached shared objects; keep serial/bay as extrinsic state passed in. 50,000 contexts, a handful of flyweights.

Level 4 — Capstone coding challenges (no peeking — there's no answer to reveal)

  1. The Custom Build pipeline: combine Builder + Decorator + Strategy — build a base robot, wrap it with two upgrades, compute its power draw under eco mode. One main(), three patterns cooperating.
  2. The Factory simulator: Abstract Factory + Facade — a FactoryOpener facade that takes any product series and runs the full production sequence.
  3. Undo everything: Command + Memento — job cards carry snapshots so "undo" restores the exact prior floor state, not just the inverse action.
  4. The smart robot: State + Observer — the robot publishes its state transitions; a maintenance dashboard observes and warns after N tasks.
  5. Floor analytics: Composite + Visitor + Iterator — walk the whole assembly tree with an iterator and let a visitor compute cost per sub-assembly.

✅ You've mastered the patterns when…

  • You can retell all 23 chapters in order and name each pattern from its story beat alone.
  • You can state every pattern's intent in one sentence without the factory metaphor.
  • You can explain the five classic confusions (Q9–Q16) to someone else.
  • Given a fresh requirement, you name a pattern AND say why two neighbors are a worse fit.
  • You've written at least one pattern from scratch in both C++ and Python without looking.
  • You can say when NOT to use a pattern — the final boss: patterns are vocabulary, not obligations. A basic bot doesn't need an AbstractSingletonProxyFactoryFacade.
